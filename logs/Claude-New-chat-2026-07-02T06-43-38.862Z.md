#### Why this is tricky



The binary is OLLVM-obfuscated (confirmed by an `OLLVM: Obfuscator` string) and its **ELF section header table is deliberately corrupted** (`e_shoff = 0xDEADBEEF`, `e_shnum = 0`), so `objdump`/`readelf` refuse to disassemble it normally. On top of that, it contains a **self-ptrace anti-debug check** — this is the "anti-debug trap" the instructor note warns about.


#### Step-by-step solution



**1. Recon**


```
file not-crypto        → PIE ELF, no section headers
strings not-crypto      → "OLLVM: Obfuscator", "I heard you wanted to bargain...",
                           "Yep, that's it!", "Access Granted!"
```


**2. Behavioral probing**

Running the binary with different stdin inputs revealed two very different outcomes:


- Empty input → `Access Granted!` (exit 31) — **this is the decoy**
- Any non-empty garbage input (`"AAAA"`, `"test"`, etc.) → `Yep, that's it!` (exit 1) — the real success message


**3. Fixing the ELF for static analysis**

I zeroed out the bogus `e_shoff`/`e_flags` fields, then extracted the LOAD segments as flat binaries (their file offsets equal their virtual addresses) and disassembled them with `objdump -D -b binary -m i386:x86-64`.


**4. Reconstructing the import table by hand**

Since `readelf -r`/`--dyn-syms` also depend on section headers, I parsed the `.dynamic` segment (`DT_SYMTAB`, `DT_STRTAB`, `DT_JMPREL`) manually in Python to recover the PLT stub → libc function mapping (`puts`, `fread`, `strstr`, `__stack_chk_fail`).


**5. Finding the real check**

The core logic decrypts a hidden blob with an XOR/S-box keystream into a stack buffer, then calls a hand-rolled `strstr(haystack = decrypted_blob, needle = your_input)`. Success (`"Yep, that's it!"`) is printed only when `strstr` returns **NULL** — i.e., when your input is *not* a substring of the decrypted blob. An **empty string is always found** (needle=="" always "matches"), which is exactly why empty input triggers the `Access Granted!` decoy, and why literally any non-empty guess "solves" the printed check. The real target of the challenge is the decrypted blob itself.


**6. Anti-debug obstacle**

Early in `_start`, the program executes a raw `syscall` equivalent to `ptrace(PTRACE_TRACEME, 0, 0, 0)`. If that fails (which it does when a debugger is already attached, since a process can only have one tracer), the program immediately calls `exit(1)` — **silently, with no output at all**. This coincidentally shares the same exit code (1) as the legitimate success path, which is exactly the "confusing output" the instructor note warns about.


**7. Bypassing it and dumping the flag**

I wrote a small Python `ptrace`-based harness (via `ctypes`) that:


- Attaches to the child before `execve` (`PTRACE_TRACEME` in the child, standard debugger pattern)
- Single-steps through syscalls (`PTRACE_SYSCALL`) and **fakes the return value of the tracee's own `ptrace()` syscall to 0** (success), defeating the anti-debug check
- Sets a software breakpoint (`0xCC`) right before the `strstr`-equivalent call
- Reads `RDI` (the haystack pointer) at that breakpoint
