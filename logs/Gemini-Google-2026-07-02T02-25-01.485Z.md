## Reference Solution: Bypassing `bypassme` via Runtime Debugging


### Objective


To intercept the password verification process at runtime and extract the dynamically generated password before the comparison happens.

### Step-by-Step Guide


#### Step 1: Analyze the Symbols


Looking at the binary's symbol table, we see several critical functions:

- `main` — The entry point.
- `_Z13auth_sequencev` (`auth_sequence()`) — Likely handles the password prompt and verification logic.
- `strcmp@@GLIBC_2.2.5` — The standard library function used to compare two strings.

Because `strcmp` takes two strings as arguments (the user's input and the correct password), setting a breakpoint on `strcmp` allows us to inspect both values in memory simultaneously.

#### Step 2: Launch the Debugger


Run the binary inside the debugger (using LLDB as recommended by the challenge description):
Bash
```

```

#### Step 3: Set a Breakpoint on `strcmp`


Tell the debugger to pause execution right when the program attempts to compare the passwords:
Plaintext
```
(lldb) breakpoint set -n strcmp
```

*Alternative:* If `strcmp` is inlined or difficult to catch, you can set a breakpoint on the authentication function: `breakpoint set -n auth_sequence`.

#### Step 4: Run the Program and Provide Input


Start the execution:
Plaintext
```
(lldb) run
```

The program will display its intro sequence and prompt you: `Enter password:`.
Input a easily identifiable dummy password, such as `AAAA` or `password123`.

#### Step 5: Inspect Registers to Leak the Password


Once you press Enter, the binary will process the input and hit the `strcmp` breakpoint.

On Linux x86_64, the system calling convention passes the first two arguments of a function inside the **RDI** and **RSI** registers:

- **Argument 1 (RDI):** Pointer to String 1
- **Argument 2 (RSI):** Pointer to String 2

To read the strings pointed to by these registers, execute:
Plaintext
```
(lldb) register read rdi rsi
```

To print the actual text stored at those memory addresses:
Plaintext
```
(lldb) x/s $rdi
(lldb) x/s $rsi
```

One of these registers will contain your dummy input (`AAAA`), while the other will display the **correct, runtime-decoded password**.

Ah, you hit an early roadblock! What happened here is a classic quirk when debugging dynamic binaries:

### Why did it stop immediately?


When the program first launches, the operating system's dynamic linker (`ld-linux-x86-64.so.2`) uses `strcmp` internally to set up the program libraries before your actual code even runs. Because you set a blanket breakpoint on `strcmp`, LLDB paused the execution inside the linker **before** the program even asked you for a password. That's why typing `1234` threw an error—the program wasn't waiting for input yet; LLDB was waiting for a command.

### How to Fix It


You need to tell LLDB to skip past these initial internal setup loops.

Instead of setting the breakpoint right at the start, follow these steps in your terminal:

1. **Restart the process and stop at `main` first:**
Plaintext
```
(lldb) b main
(lldb) r
```

*(This ensures the program finishes initializing everything and stops safely at the beginning of your code.)*
2. **Now, set the breakpoint on `strcmp`:**
Plaintext
```
(lldb) b strcmp
```
3. **Continue the program:**
Plaintext
```
(lldb) c
```
4. **Provide your input:**
The program will now run normally, print the intro text, and ask you to `Enter password:`.
Type `1234` (or any dummy text) and hit **Enter**.
5. **Read the password from memory:**
The program will hit your `strcmp` breakpoint. Now you can safely extract the values! In LLDB, run:
Plaintext

(lldb) x/s $rdi
