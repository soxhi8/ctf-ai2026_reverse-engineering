### What the program does



`reader()` treats the song text as a tiny bytecode program:


- `song_lines` is the whole song (including the hidden `secret_intro` containing the flag) split into lines.
- It scans for three labels:

  - `startLabel` (`[VERSE1]`) → where execution begins
  - `[REFRAIN]` → the refrain subroutine's entry point
  - `RETURN` → the line used to store a "return address" when jumping into the refrain
- The interpreter walks line by line (`lip` = "line instruction pointer"), executing:

  - `REFRAIN` → saves `lip+1` into the `RETURN` line as `RETURN <n>`, then jumps to the refrain
  - `CROWD (Singalong here!)` → reads user input, stores it back into that very line as `Crowd: <input>`
  - `RETURN <n>` → jumps to line `n`
  - `END` → stops
  - anything else → prints the line


**Key bug:** the flag lines (from `secret_intro`) live at the very *top* of `song_lines`, before `[VERSE1]`. The interpreter starts at `[VERSE1]` and never walks over those lines through normal flow. But when the refrain runs, it does `input('Crowd: ')` and stores it as `song_lines[lip] = 'Crowd: ' + crowd` — the raw text of whatever we type, unescaped, becomes literal content of the script's "instruction stream."


That means we can make the CROWD line itself become a `RETURN <n>` instruction, jumping the instruction pointer to line 0 (or wherever the flag lives), and the interpreter will just start printing from there — walking straight through the flag lines and into the rest of the song.


### Exploit



When prompted `Crowd:` for input, send:


```
RETURN 0
```


Because the code does `song_lines[lip] = 'Crowd: ' + crowd`, this becomes the line `Crowd: RETURN 0`, which does **not** match `re.match(r"RETURN [0-9]+", line)` (since the line starts with `Crowd: `, not `RETURN`)! So we need to be cleverer.


Look again at how CROWD is matched: `re.match(r"CROWD.*", line)` — it matches on the *original* line before rewriting only the first time. On subsequent visits to that same `lip`, the line has been rewritten to `Crowd: <input>` and will be re-parsed as `Crowd: <input>` on the *next* pass over it (e.g. after another `REFRAIN` loop revisits that line). At that point:


- If our input made the full line become something matching `RETURN [0-9]+` when prefixed with `Crowd: `, it still won't match, since the regex isn't anchored with re.search — `re.match` anchors at the start of the string. So embedding `RETURN 0` after `Crowd: ` won't trigger the RETURN branch directly.


**Better approach — use the `;` splitting.** Each `song_lines[lip]` is split on `;` before being interpreted, and multiple "instructions" can live on one physical line separated by `;`. Since our crowd input is inserted verbatim as `'Crowd: ' + crowd`, if we make `crowd` itself supply a `;`-separated payload where an early segment is empty/junk and a later one is a bare `RETURN 0`, the **next time this same line is executed** (which happens because the refrain always returns to right after the CROWD line, and the song loops back through `REFRAIN` multiple times, revisiting line `lip`), the split will produce multiple parts, one of which can be `RETURN 0` verbatim.


Concretely, since the stored line is `Crowd: <our input>`, splitting on `;` gives parts like `Crowd: <part1>`, `<part2>`, `<part3>`, etc. Only the *first* part keeps the `Crowd: ` prefix; later parts are exactly what we typed. So if we type:


```
x;RETURN 0
```


The line becomes `Crowd: x;RETURN 0`. Split on `;`: `["Crowd: x", "RETURN 0"]`.


- First iteration (this pass, right after prompting): the code only handles **one** branch per call to `input()` — but actually look closer: the `for line in song_lines[lip].split(';')` loop reads the **line as it exists at the moment of entry into that iteration of the while-loop**, i.e. it reads the *original* unmodified line first (`CROWD (Singalong here!)`), matches CROWD, prompts, rewrites `song_lines[lip]`, and increments `lip` — the inner `for` loop only had one part (`CROWD (Singalong here!)`) that iteration, since splitting happened before the rewrite. So our `;RETURN 0` payload isn't processed immediately.
- However, the refrain is called **6 times** in the song (once per verse). Each time `REFRAIN` runs, it overwrites the `RETURN` label line with `RETURN <new lip>`, then jumps to `[REFRAIN]`, prints the 4 refrain lines, hits `CROWD (Singalong here!)` **again at the same `lip`** — but wait, this is the *same physical line index* every time (the CROWD line is fixed at one position in `song_lines`), and by the second time we reach it, `song_lines[lip]` has already been overwritten to `Crowd: x;RETURN 0` from our first answer. This time, `song_lines[lip].split(';')` yields `["Crowd: x", "RETURN 0"]` — two parts! The loop processes `"Crowd: x"` (matches `CROWD.*`? No — `"Crowd: x"` does **not** match `^CROWD.*` since it's lowercase `Crowd`, not `CROWD`; and it doesn't match RETURN either) — it falls to the `else` branch and just **prints** `"Crowd: x"`, incrementing `lip`. Then it processes `"RETURN 0"` — matches `RETURN [0-9]+` → **`lip = 0`**.


That's the jump we want.
