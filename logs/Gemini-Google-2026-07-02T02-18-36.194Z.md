## 2. Step-by-Step Solution Using a Debugger (LLDB/GDB)


Since the binary must decode the password to perform a standard string comparison (`strcmp`), the easiest and most reliable way to solve this is via **Dynamic Analysis**. Students can intercept the password in memory right before or during the comparison phase.

### Step 1: Fire up the Debugger


Run the binary inside a local debugging environment (or the provided Docker container if tools are installed):
Bash
```
lldb ./bypassme.bin
```

*(If using GDB, substitute `lldb` with `gdb ./bypassme.bin`)*

### Step 2: Set a Breakpoint on `strcmp`


Because the application uses `strcmp` to validate the user's password against the correct one, setting a breakpoint here will catch the password in its completely plaintext, decoded form.

**In LLDB:**
Plaintext
```
(lldb) breakpoint set --name strcmp
```

**In GDB:**
Plaintext
```
(gdb) break strcmp
```

### Step 3: Run the Program and Provide Dummy Input


Start execution. When prompted with `Enter password:`, enter a recognizable dummy string (e.g., `AAAA`).

**In LLDB / GDB:**
Plaintext
```
(lldb) run
```

### Step 4: Inspect the Registers / Arguments


Once the breakpoint hits, the program will pause exactly when entering `strcmp`. According to the x86_64 calling convention, the two strings being compared are passed into the first two architecture registers:

- `$rdi` (Argument 1: Typically the user's input or the correct password)
- `$rsi` (Argument 2: The opposing string)

Print the contents of these registers as strings to reveal the flag/password:

**In LLDB:**
Plaintext
```
(lldb) register read rdi rsi
(lldb) x/s $rdi
(lldb) x/s $rsi
```

**In GDB:**
Plaintext
```
(gdb) info registers rdi rsi
(gdb) x/s $rdi
(gdb) x/s $rsi
```

One of these registers will display your dummy input (or its sanitized version), and the other register will explicitly reveal the **correct, decoded plaintext password**.

Ah, a classic dynamic analysis trap! What you're running into here is **linker noise**.

When a binary starts up, the dynamic linker (`ld-linux-x86-64.so.2`) internally calls `strcmp` multiple times to resolve external libraries and function addresses before the actual program code (`main`) even begins executing. Since you set a generic breakpoint on `strcmp`, the debugger is hitting those early dynamic linker calls instead of your program's authentication check.

Since you have access to GDB and the binary has debug symbols (`Reading symbols from ./bypassme.bin...`), you can bypass the linker noise entirely by catching the exact password function.

Here is how to extract the password directly, along with why it works:

## The Clean Solution (Using Function Breakpoints)


Instead of breaking on `strcmp`, set a breakpoint right inside the application's unique sequence functions. Based on your symbol table, the function `decode_password` or `auth_sequence` handles the validation.

### Step-by-Step Execution in GDB


1. **Fire up GDB with the binary:**
Bash
```
gdb ./bypassme.bin
```

Instead of catching library code, this breaks inside the exact custom logic.
Plaintext

Plaintext

*The program will execute the intro sequences, prompt you for the password, or dynamically decrypt it in memory, pausing exactly inside `decode_password`.*
4. **Step out of the decoding function:**
Once you hit the breakpoint, the function is starting. To let it complete its decoding routine and see the final product, execute the `finish` command to run until the function returns:

5. **Examine the string arguments or memory:**
